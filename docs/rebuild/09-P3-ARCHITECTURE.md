# P3 Architecture — Private Documents and Inspectable Sources

**Branch:** `agent/p3-document-sources`  
**Status:** In progress  
**Depends on:** P1 account/workspace/RLS foundation and P2 persistent conversation foundation  
**Phase goal:** deliver one honest, workspace-isolated document path from upload to inspectable supporting passage without creating a second identity, storage, or retrieval authority.

## Product outcome

P3 must let an authorized user:

1. upload a supported document to an active workspace;
2. see explicit validation and processing state;
3. reload and find the same persisted document;
4. search its extracted passages;
5. open the exact supporting passage and locator;
6. delete the original object and its derived passages;
7. receive explicit unsupported, invalid, failed, duplicate, forbidden, and unavailable states.

The later P3 grounded-answer slice will add source selection and persistent citations to the P2 conversation path. The storage/extraction/source foundation must be trustworthy before an answer is allowed to claim grounding.

## Initial supported formats

The first vertical slice deliberately supports only bounded UTF-8 text:

- plain text: `.txt`, normalized media type `text/plain`;
- Markdown: `.md` or `.markdown`, normalized media type `text/markdown`.

Initial file limit: **2 MiB per object**.

The following remain unsupported until a real parser, worker boundary, security review, and fixtures are implemented:

- PDF;
- DOCX and other office formats;
- scans and OCR;
- images;
- spreadsheets;
- presentations;
- archives;
- audio and video.

Unsupported formats are rejected before persistence. The product must not label a placeholder, filename guess, or model-generated summary as extraction.

## Audit result: inherited document implementation

The inherited FastAPI document route, models, and service are not reused for P3.

Observed problems:

- document records are held in process memory;
- uploaded bytes are read but never persisted by the service;
- storage URLs and presigned URLs are fabricated;
- processing sleeps and returns placeholder AI/OCR metadata;
- a model label is returned without a real provider call;
- no actual PDF, office, OCR, text extraction, chunking, retrieval, or citation implementation exists;
- status values differ from the canonical PostgreSQL attachment contract;
- response models and service output shapes diverge;
- the service uses a separate authentication and data authority from P1/P2;
- there is no workspace RLS, duplicate control, private-object policy, durable failure state, or deletion reconciliation.

The inherited API remains audit/quarantine scope. It may contribute only after a file-level provenance review and executable tests prove a specific reusable part.

## Authoritative boundaries

### 1. Identity and authorization

Supabase Auth remains the only account/session identity authority.

Next.js route handlers and server components use the request-scoped signed-in Supabase client. PostgreSQL RLS and Storage object policies enforce workspace membership and role. Normal document requests do not use `SUPABASE_SERVICE_ROLE_KEY`.

Authorization matrix:

| Capability | Owner | Editor | Viewer |
| --- | ---: | ---: | ---: |
| List documents and passages | Yes | Yes | Yes |
| Download original through authorized/signed access | Yes | Yes | Yes |
| Search passages | Yes | Yes | Yes |
| Upload and process | Yes | Yes | No |
| Retry failed processing | Yes | Yes | No |
| Delete document and derived passages | Yes | Yes | No |

Archived workspaces are read-only for every role.

### 2. Object storage

Supabase Storage owns original file bytes.

A single private bucket is used for P3 workspace documents. It is not public. Object paths are generated by the application rather than derived from the user filename:

```text
<workspace-id>/<attachment-id>/document.txt
<workspace-id>/<attachment-id>/document.md
```

The original filename remains metadata in PostgreSQL.

Bucket and object policies:

- the first folder segment must be a workspace UUID;
- workspace members may select/download objects;
- owner/editor may insert and delete objects;
- viewers cannot upload, replace, or delete;
- archived workspace uploads are rejected by application and database state guards;
- bucket-level MIME and size restrictions match the application contract.

Object operations use the Storage API. Application code does not directly create, update, or delete rows in `storage.objects`.

### 3. Metadata and passages

PostgreSQL remains authoritative for:

- attachment identity and lifecycle;
- original filename and normalized media type;
- byte count and content hash;
- storage path;
- processing state and failure code;
- processor version and attempt history;
- extracted source passages and locators;
- search indexes;
- later message-to-source citations.

The P1 `attachments` and `sources` tables are extended rather than replaced.

### 4. Synchronous first processor

The first processor runs synchronously inside a bounded Next.js route because:

- supported objects are at most 2 MiB;
- decoding is deterministic UTF-8 work;
- no OCR, office parser, sandbox, network request, or model is involved;
- the result can be finalized in one request with explicit cleanup on failure.

A durable processing-attempt table is still introduced so the state model can later move to an idempotent worker without changing the product contract.

PDF, office, OCR, archive, and other expensive or unsafe formats require a separate worker boundary and are not added to this synchronous path.

## Upload contract

### Request

A same-origin route accepts `multipart/form-data` with one file under an authorized workspace route.

The route validates before object upload:

1. authenticated user;
2. workspace membership and owner/editor role;
3. active workspace state;
4. exactly one file;
5. non-empty filename no longer than 255 characters;
6. supported extension and declared media type;
7. byte size from 1 byte through 2 MiB;
8. strict UTF-8 decoding with fatal error behavior;
9. removal of a leading UTF-8 BOM;
10. rejection of NUL and disallowed control characters;
11. non-empty normalized text;
12. bounded line length;
13. SHA-256 duplicate check inside the workspace.

The route never trusts client-provided workspace, uploader, size, storage path, status, hash, or processor fields.

### Duplicate definition

`content_sha256` is calculated over the original bytes.

An active `pending`, `processing`, or `ready` attachment with the same workspace and hash is a duplicate. Failed or deleted records do not permanently block a later clean upload.

The database enforces the active duplicate rule with a partial unique index. The application converts a uniqueness race into a stable duplicate response.

### Filename handling

User filenames are display metadata only.

They are:

- trimmed;
- stripped of path components;
- rejected when empty, too long, or containing NUL;
- never interpolated into the storage path;
- rendered as text, not HTML.

## Text normalization and deterministic chunking

### Normalization

After strict UTF-8 decode:

- one leading BOM is removed;
- CRLF and CR are normalized to LF;
- trailing spaces at line ends may be removed without changing line count;
- the complete normalized document is not stored in a separate unbounded database field;
- source passages retain exact offsets into the normalized text used by the processor.

### Passage contract

Each source passage stores:

- stable ordinal starting at zero;
- content;
- start offset, inclusive;
- end offset, exclusive;
- start line and end line, one-based;
- page number only when a future parser provides a real page number;
- processor version through its parent processing attempt.

Text and Markdown passages never receive invented page numbers.

### Chunking strategy

The first chunker is deterministic and paragraph-aware:

- target passage size is bounded;
- blank-line paragraph boundaries are preferred;
- overlong paragraphs are split at line, sentence, or whitespace boundaries;
- an overlong token is split safely by character count;
- no passage is empty;
- ordinals and offsets are reproducible for the same normalized text and processor version;
- Arabic, English, mixed text, numbers, URLs, and code-like lines are preserved.

The first version does not use model-based chunking.

## Processing lifecycle

Attachment states remain:

- `pending`;
- `processing`;
- `ready`;
- `failed`;
- `deleted`.

A processing attempt records:

- attachment and workspace;
- attempt number;
- processor name/version;
- pending/processing/complete/failed status;
- source count and character count;
- stable failure code and bounded detail;
- start and completion timestamps.

Expected stable failure codes include:

- `UNSUPPORTED_FILE_TYPE`;
- `FILE_EMPTY`;
- `FILE_TOO_LARGE`;
- `MEDIA_TYPE_MISMATCH`;
- `INVALID_UTF8`;
- `DISALLOWED_CONTROL_CONTENT`;
- `LINE_TOO_LONG`;
- `DUPLICATE_DOCUMENT`;
- `STORAGE_UPLOAD_FAILED`;
- `EXTRACTION_FAILED`;
- `SOURCE_PERSISTENCE_FAILED`;
- `STORAGE_DELETE_FAILED`;
- `PERSISTENCE_ERROR`.

Success is shown only after the object, attachment metadata, processing attempt, and passages have all reached their durable final state.

## Atomic source finalization

A PostgreSQL function finalizes one processing attempt by:

1. validating caller workspace role;
2. validating attachment and attempt ownership/state;
3. replacing only that attachment's passages;
4. inserting ordered validated passages;
5. marking the attempt complete;
6. marking the attachment ready;
7. recording processed time and source count;
8. touching workspace/document timestamps.

Failure rolls back the database changes. The route then attempts Storage cleanup and records an explicit failed state when cleanup cannot complete.

## Retrieval

### Initial retrieval engine

P3 begins with PostgreSQL full-text search using an explicit `simple` text-search configuration.

Reasons:

- it preserves Arabic and English tokens without assuming language-specific stemming;
- it is deterministic and available in the existing PostgreSQL boundary;
- it avoids adding an embedding provider, vector store, cost claim, or quality claim before benchmark data exists.

Each passage has a stored search vector and GIN index.

The workspace search function:

- validates membership through RLS/session context;
- searches only ready, non-deleted attachments in one workspace;
- accepts a bounded query and result limit;
- returns source ID, attachment ID, filename, ordinal, content, line/page locator, and rank;
- uses deterministic tie-breaking;
- never searches another workspace.

Embeddings and hybrid ranking remain a later measured improvement. They are not required merely because inherited files mention RAG or vector services.

## Inspectable source viewer

P3 routes:

```text
/workspaces/<workspace-id>/sources
/workspaces/<workspace-id>/sources/<attachment-id>
```

The list shows persisted attachment status, type, size, upload time, processing state, passage count, and failure reason when relevant.

The detail page shows:

- original filename and metadata;
- authorized original-file download action;
- every extracted passage in ordinal order;
- real line range or future page range;
- a stable anchor for each source ID;
- neighboring context;
- explicit unavailable/deleted/failure states.

A search result links directly to the selected source anchor.

## Deletion lifecycle

Delete is a coordinated operation:

1. verify owner/editor access and active workspace;
2. mark the attachment deletion operation in progress;
3. delete the private Storage object through the Storage API;
4. delete the attachment row, cascading sources and processing attempts;
5. return success only after both object and metadata deletion succeed.

If Storage deletion fails, database metadata remains and the UI shows an explicit retryable failure. The route does not claim deletion while bytes remain.

Conversation text generated from a document may remain until its conversation is deleted. The later citation model must show a deleted/unavailable source rather than silently linking to another passage.

## Grounded conversation integration — later P3 slice

Grounding is opt-in and explicit.

A grounded turn will:

1. search ready sources inside the conversation workspace;
2. fail honestly when no relevant source exists;
3. provide bounded labelled passages to the P2 provider adapter;
4. require valid labels such as `[S1]` in the answer;
5. persist message-to-source citation records;
6. render each citation as a link to the exact passage;
7. never describe an ungrounded provider answer as document-grounded.

The storage/source foundation is implemented and validated before this integration is enabled.

## Security and abuse controls

The initial slice includes:

- private bucket only;
- RLS-backed folder policies;
- generated object paths;
- strict size/type/UTF-8 checks;
- no archive expansion;
- no executable or browser-rendered upload types;
- no HTML rendering from document content;
- no model or network processing during extraction;
- bounded filenames, lines, chunks, query length, result count, and failure details;
- no service-role key in browser or ordinary route logic;
- cross-account and cross-workspace regression tests;
- deletion verification.

This is not malware certification. Future complex parsers require sandboxing, resource limits, decompression limits, parser patch management, and malicious fixtures.

## P3 completion boundary

The source foundation is complete only when:

- supported files are private and durably stored;
- validation failures are explicit and leave no falsely ready record;
- deterministic passages survive reload;
- search returns only authorized workspace passages;
- a result opens the exact real locator;
- viewer and outsider restrictions hold across database, API, page, and Storage;
- deletion removes both object bytes and derived passages;
- P0–P2 regressions and all P3 data, Storage, contract, build, and browser gates pass.

Full P3 is complete only after the later grounded-conversation slice also persists and resolves citations to these inspectable passages.

P3 completion is not production readiness, parser security certification, retrieval-quality certification, or provenance clearance.
